# Mindex Data Engineering & Data Architecture Code Challenge Solution

## Executive Summary

This repository contains an end-to-end, production-minded Python 3.10+ and SQLite ETL/ELT pipeline built for Mindex Technologies. The pipeline ingests raw legacy CSV exports (`transactions.csv`, `stores.csv`, `products.csv`), profiles dataset quality, applies defensible data cleaning and validation across **17 distinct defect classes**, loads a normalized **Star Schema Data Warehouse (`output/warehouse.db`)**, executes 5 core business intelligence queries + 1 revenue reconciliation query (`output/analytics.json`), and provides a comprehensive `pytest` test suite with 100% pass rate across 27 tests.

In addition, a **Next.js + React + Tailwind CSS interactive dashboard** (`dashboard/`) is included to visualize data quality findings, lineage, star schema structure, and SQL analytics linked directly to source code annotations.

## 📐 Star Schema Data Warehouse Design (`output/warehouse.db`)

The warehouse implements a **Star Schema** in SQLite with 4 conformed dimensions and 1 atomic fact table:

```
                  ┌───────────────────────────────┐
                  │           dim_date            │
                  ├───────────────────────────────┤
                  │ PK  date_key (INTEGER yyyymmdd│
                  │     full_date (TEXT ISO)      │
                  │     year, quarter, month      │
                  │     year_month (TEXT 'YYYY-MM')│
                  │     month_name, day_of_month  │
                  │     day_of_week, is_weekend   │
                  └───────────────┬───────────────┘
                                  │ 1:N
                                  ▼
┌──────────────────────────┐ 1:N ┌──────────────────────────────┐ N:1 ┌─────────────────────────────┐
│        dim_store         │────>│          fact_sales          │<────│         dim_product         │
├──────────────────────────┤     ├──────────────────────────────┤     ├─────────────────────────────┤
│ PK  store_key (INTEGER)  │     │ PK  sales_key (INTEGER)      │     │ PK  product_key (INTEGER)   │
│ UNIQUE store_id (TEXT)   │     │ Degenerate transaction_id    │     │ UNIQUE product_id (TEXT)    │
│     store_name, city     │     │ FK  date_key (INTEGER)       │     │     product_name, category  │
│     state, zip_code      │     │ FK  store_key (INTEGER)      │     │     category_is_imputed     │
│     zip_is_suspect       │     │ FK  product_key (INTEGER)    │     │     list_unit_price (REAL)  │
│     region               │     │ FK  customer_key (INTEGER)   │     │     price_is_imputed        │
│     region_is_imputed    │     │     quantity (INTEGER)       │     │     price_conflict          │
│     opened_date          │     │     unit_price (REAL)        │     │     supplier_id             │
└──────────────────────────┘     │     extended_amount (REAL)   │     └─────────────────────────────┘
                                 │     discount_amount (REAL)   │
┌──────────────────────────┐ 1:N │     net_amount (REAL)        │
│       dim_customer       │────>│     is_return (INTEGER 0/1)  │
├──────────────────────────┤     └──────────────────────────────┘
│ PK  customer_key(INTEGER)│
│ UNIQUE customer_id (TEXT)│
│     is_guest (INTEGER 0/1│
└──────────────────────────┘
```

### Key Modeling Decisions

1. **Surrogate Integer Primary Keys (`*_key`)**:
   - Every dimension assigns an autoincrementing integer primary key while enforcing `UNIQUE` constraints on natural source keys (`store_id`, `product_id`, `customer_id`).
   - *Rationale*: Isolates warehouse analytics from source key instability (e.g., S007 duplicate PKs) and provides performance optimization for integer joins.

2. **Price Drift & Historical Pricing**:
   - `dim_product.list_unit_price` stores the master catalog price.
   - `fact_sales.unit_price` stores the transacted price at the moment of sale.
   - *Rationale*: Prevents historical sales figures from silently changing whenever catalog list prices update.

3. **Returns Modeling (`is_return=1`)**:
   - Return transactions (TX-10) are stored in `fact_sales` with negative `quantity` and negative `net_amount`, accompanied by `is_return=1`.
   - *Rationale*: `SUM(net_amount)` natively computes Net Revenue without custom query logic or sign-reversal hazards.

4. **Dense Calendar Dimension (`dim_date`)**:
   - Pre-populated for all 90 calendar days in the transaction window, even days without sales.
   - *Rationale*: Guarantees accurate month-over-month growth calculations and prevents zero-sales periods from vanishing in time-series aggregations.

## 📈 Business Analytics Implementation

All 5 core queries + 1 revenue reconciliation query are implemented in **declarative SQL** in `src/analytics/queries.py` and executed by `src/analytics/runner.py`.

### 1. Top 5 Stores by Net Revenue (Trailing 30 Days)
- **SQL Logic**: `SUM(net_amount)` filtered by `dim_date.full_date BETWEEN :window_start AND :as_of_date`. Returns automatically reduce revenue via negative signed amounts.
- **Top Performer**: *The Domain (South)* led with **$2,072.94** net revenue.

### 2. Month-over-Month Revenue Change (%) by Product Category
- **SQL Logic**: Uses window function `LAG(monthly_revenue) OVER (PARTITION BY category ORDER BY year_month)` and `NULLIF(prev_month_revenue, 0)` to handle zero baselines safely.

### 3. Store Return Rate (% Return Transactions & Unit-Based)
- **SQL Logic**: Computes both transaction-count return rate (`return_txns / total_txns`) and unit-based return rate (`returned_units / total_units`). Flags stores where unit return rate exceeds 10%.
- **Alert Flagged Stores**: *Alderwood Mall (15.38%)*, *Galleria at Crystal Run (13.16%)*, and *Lakeside Shopping Ctr (12.50%)*.

### 4. Average Transaction Value by Region
- **SQL Logic**: `AVG(net_amount)` filtered by `is_return = 0`.
- **Top Performer**: *Northeast* led with **$392.45** average order value.

### 5. Top 10 Customers by Lifetime Spend
- **SQL Logic**: `SUM(net_amount)` grouped by `customer_id`, excluding `dim_customer.is_guest = 1`.
- **Top Customer**: `CUST0213` with **$2,966.04** lifetime spend across 3 orders ($988.68 AOV).

### 6. Revenue Reconciliation (TX-03 Proof)
- **SQL Logic**: Reconciles `gross_list_value` ($170,816.34) - `discount_total` ($1,104.05) - `returns_value` ($11,668.00) = `net_revenue` ($158,044.29).
- **Delta**: **$0.00** — proves 100% arithmetic reconciliation across all 474 warehouse transactions.

### Test Coverage Highlights (27/27 Passing)
- **`tests/test_profiler.py` (8 tests)**: Validates row/col counts, null percentages, duplicate row counts, numeric min/max/mean, empty DataFrames, 100% all-null columns, and `TypeError` on invalid inputs.
- **`tests/test_cleaning.py` (14 tests)**: Validates ZIP padding (ST-01), near-duplicate survivorship (ST-02), region imputation (ST-03), exact dupes (PR-01), price conflicts (PR-02), null categories (PR-03), zero prices (PR-04), multi-format date parsing (TX-01), regex currency parsing (TX-02), discount preservation (TX-03), orphan exclusions (TX-04/05), guest sentinels (TX-06), zero-qty exclusions (TX-07), future date exclusions (TX-08), and return flags (TX-10).
- **`tests/test_analytics.py` (5 tests)**: Seeds an in-memory SQLite warehouse fixture with hand-calculated transactions and asserts exact query output for return rates, net revenue, GUEST exclusions, AOV by region, and zero-delta revenue reconciliation.

## 🚀 Productionization & Scaling Strategy

If deploying this pipeline to production at Mindex, the following architectural upgrades should be made:

1. **Orchestration & Lineage (Dagster / Apache Airflow)**:
   - Encapsulate stages as Dagster Software-Defined Assets (`raw_csv -> profile_report -> clean_df -> warehouse_db -> analytics_json`).
   - Configure automatic PagerDuty alerts if defect detection counts diverge from historical baselines.

2. **Data Quality & Schema Testing (dbt + Great Expectations)**:
   - Migrate SQL transformations and dimension loading into `dbt` models with `not_null`, `unique`, and `relationships` test assertions.

3. **Incremental Ingestion (CDC + Partitions)**:
   - Transition from full reloads to Change Data Capture (Debezium / AWS DMS) appending daily partitions to `fact_sales`.

4. **Cloud Infrastructure (AWS Fargate + Snowflake / BigQuery)**:
   - Containerize the pipeline into Docker images on AWS Fargate.
   - Target Snowflake or BigQuery for enterprise analytical scaling beyond single-node SQLite.

- Python 3.10+

